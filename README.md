## Что это такое

**Podkop BearGuard** — веб-интерфейс и набор служебных компонентов для управления Telegram-ботом [**podkop_bot**](https://github.com/Medvedolog/podkop_bot), Podkop/Forkop и связанными сетевыми службами на роутерах OpenWrt.

Техническое имя устанавливаемого LuCI-пакета пока остаётся **`luci-app-podkop-bot`**. Внутренние UCI, RPC/ubus-объекты и пути `podkop_bot*` также сохраняются ради совместимости; BearGuard — пользовательское имя приложения, а не массовое переименование внутренних API.

BearGuard помогает установить, восстановить и обновить бота, проверить его связь с Telegram и GitHub, посмотреть состояние Podkop или Forkop, определить активный маршрут, проверить доступность внешних служб и управлять дополнительными сетевыми возможностями.

Начиная с ветки 0.19.19 приложение также умеет работать со встроенным в sing-box Tailscale/tsnet. Поддерживаются обычный Podkop, Forkop и Forkop X. Там, где проект уже предоставляет штатную Tailscale-интеграцию, используется именно она. Для Podkop и Forkop X исходные проекты не патчатся: BearGuard меняет текущий runtime-конфиг sing-box и, по желанию пользователя, может автоматически вернуть потерянный endpoint после штатной перегенерации конфигурации.

Автовосстановление Tailscale не использует постоянный watcher. Раз в минуту короткий cron-helper проверяет, нужен ли repair; перед повторным применением он ждёт окончания reload Forkop и подтверждает готовность dataplane реальной прикладной пробой через Main/Backup Mixed Proxy. После попытки действует cooldown, поэтому механизм не превращается в цикл перезапусков.

Конфигурация маршрутизации Podkop и его форков по-прежнему остаётся их зоной ответственности. BearGuard читает необходимые параметры для диагностики и транспорта, а изменения выполняет только там, где для этого предусмотрена отдельная функция: например, настройка Tailscale/tsnet, включение Mixed Proxy, управление фильтрами Forkop или явное обновление установленного варианта Podkop.

## Основные возможности

- установка, восстановление, обновление и удаление `podkop_bot`;
- настройка Telegram-бота и проверка токена;
- автоматическое определение Podkop, Podkop Plus, Forkop, Forkop X и NetShift;
- выбор пути к Telegram и GitHub через прямое соединение или прокси;
- диагностика активных маршрутов, выходного IP, страны, провайдера и задержек;
- проверка доступности популярных служб через выбранный маршрут;
- управление встроенным Tailscale/tsnet в sing-box без обязательной установки отдельного `tailscaled`;
- поддержка получения маршрутов Tailscale и объявления роутера как выходного узла;
- штатная Tailscale-интеграция там, где она доступна, и runtime-интеграция для Podkop/Forkop X без постоянного watcher-процесса;
- опциональное автовосстановление tsnet после перегенерации Podkop/Forkop X с readiness-проверкой через Main/Backup Mixed Proxy;
- WARP Rescue и Warpscout для резервного доступа и диагностики;
- Bearhole для аварийного многопрокси-доступа;
- работа с OpenWrt 24.10 через IPK и с OpenWrt 25.12+ через APK.

## Как это устроено

Приложение разделено на веб-интерфейс LuCI и несколько служебных компонентов `rpcd`.

- `rpcd` принимает команды из LuCI, проверяет параметры и выполняет системные действия.
- `/usr/lib/podkop_bot/install.sh` устанавливает, обновляет, проверяет и удаляет Telegram-бота.
- отдельные обработчики обслуживают диагностику, Bearhole, Warpscout и Tailscale/tsnet.
- веб-интерфейс сам не изменяет системные файлы: он обращается к соответствующим методам `rpcd` и показывает результат пользователю.

### Установщик бота

`install.sh` поставляется вместе с приложением и соответствует установщику из репозитория [podkop_bot](https://github.com/Medvedolog/podkop_bot). Он написан для POSIX `ash` и совместим с BusyBox.

Основные действия:

- **`status`** — собирает сведения о боте, Podkop/Forkop, OpenWrt, пакетном менеджере и конфигурации;
- **`install`** — устанавливает бота и настраивает его автоматический запуск;
- **`update`** — обновляет бота;
- **`check`** и **`check-token`** — проверяют окружение и токен Telegram;
- **`uninstall`** — удаляет бота.

При недоступности GitHub приложение может использовать уже встроенную копию бота. Поэтому восстановление не зависит от того, доступен ли GitHub напрямую в данный момент.

## Tailscale/tsnet

Версия 0.19.19 добавляет управление Tailscale, встроенным непосредственно в sing-box через `tsnet`.

Приложение определяет установленный вариант Podkop/Forkop и выбирает наиболее нативный из доступных способов. Полный Forkop использует собственную UCI-модель `server/tailscale` и сам управляет перезапуском. Для Podkop и Forkop X их исходный код и UCI не изменяются: BearGuard меняет только текущий JSON sing-box при создании, включении, изменении параметров, удалении или явном повторном применении Tailscale endpoint.

Постоянного watcher-процесса для Tailscale нет. Если штатная перегенерация Podkop/Forkop X затёрла endpoint, LuCI показывает состояние `degraded` и кнопку **«Применить заново»**.

Дополнительно можно включить **автовосстановление после перегенерации Podkop/Forkop**. Это не daemon и не procd-respawn: cron вызывает короткий helper раз в минуту. Helper ничего не делает, если endpoint на месте, Tailscale выключен или идёт reload Forkop. Если endpoint потерян, он получает runtime-секции, проверяет сначала основной Mixed Proxy, затем резервный runtime-capable Mixed Proxy и разрешает reapply только после реального успешного Telegram-запроса через один из них. Между попытками действует cooldown 5 минут.

Доступны:

- создание и удаление подключения;
- включение и отключение Tailscale;
- выбор сервера управления, включая Headscale;
- имя узла;
- получение маршрутов, объявленных другими узлами;
- объявление роутера как выходного узла;
- ручное повторное применение endpoint;
- опциональное автовосстановление endpoint после перегенерации конфигурации;
- просмотр фактического состояния sing-box, подключённых узлов и применённой конфигурации.

Изменение текущего JSON выполняется через временный файл и атомарную замену. При ошибке перезапуска sing-box предыдущая конфигурация восстанавливается. BearGuard не держит отдельный процесс, который непрерывно следит за файлом и конкурирует с Podkop/Forkop за владение lifecycle sing-box.

Отдельный `tailscaled` для этого режима не требуется. Если в системе уже существует самостоятельная установка Tailscale, приложение показывает её состояние отдельно, чтобы пользователь видел возможный конфликт двух реализаций.

## Разделы интерфейса

### Обзор

Сводка состояния системы: работает ли бот, включён ли его автоматический запуск, какие версии бота, Podkop/Forkop и sing-box установлены, доступен ли GitHub, какой прокси используется и сколько ресурсов потребляют основные процессы.

### Настройки

Параметры Telegram-бота: токен, идентификаторы администраторов, доверенные группы, уведомления и наблюдение за состоянием. Опасные действия требуют отдельного подтверждения.

### Транспорт

Показывает, каким путём бот обращается к Telegram и GitHub. Можно использовать автоматический выбор, прямое соединение или прокси. Видна вся цепочка резервирования: основной прокси, дополнительные маршруты и прямое подключение.

Приложение умеет автоматически находить подходящие прокси-секции разных вариантов Podkop/Forkop, поэтому пользователю не требуется знать их внутренние имена.

### Мастер настройки

Пошаговая первоначальная установка или восстановление бота. Мастер проверяет OpenWrt, пакетный менеджер, установленный вариант Podkop/Forkop, доступность сети и существующую конфигурацию, после чего предлагает необходимые параметры.

### Состояние служб

Раздел для текущей диагностики. Здесь можно увидеть активный сервер и маршрут, протокол, задержку, выходной IP, страну, провайдера, тип адреса и состояние sing-box.

Отдельно проверяется доступность Telegram, GitHub, Claude, YouTube, ChatGPT, Gemini, Netflix, Spotify, TikTok, Twitch, Apple и Discord. Для части служб определяется регион, который они видят на выходе туннеля.

Можно проверить:

- отдельную секцию Podkop/Forkop;
- основной и резервные транспортные маршруты;
- пользовательский SOCKS5, HTTP или HTTPS-прокси без сохранения его в настройках;
- все обнаруженные маршруты одной командой.

Проверки выполняются параллельно и имеют общий предел времени, чтобы одна недоступная служба не задерживала всю страницу.

Набор этих проверок появился не с нуля. Значительная часть практических приёмов, используемых для проверки Telegram, GitHub, видеосервисов и других внешних площадок, пришла из `podkop_bot`, а там формировалась с оглядкой на открытые инструменты сообщества, в том числе WARPSCOUT. В LuCI эти проверки были переработаны под параллельный запуск, общий предел времени, работу через выбранный маршрут и единое представление результата. В конце README перечислены проекты, у которых заимствовались идеи, способы проверки доступности и отдельные технические приёмы.

### Tailscale

Показывает состояние встроенного Tailscale/tsnet и позволяет управлять им из LuCI. Здесь видны выбранный провайдер интеграции, имя узла, сервер управления, состояние получения маршрутов, режим выходного узла, число активных соединений и список подключённых узлов.

Для полного Forkop используется штатная серверная интеграция. Для Podkop и Forkop X изменения применяются только к текущей runtime-конфигурации sing-box; если сам провайдер позднее пересобрал JSON, LuCI покажет endpoint как неприменённый и, при включённом auto-repair, вернёт его после подтверждения готовности Mixed Proxy.

### WARP Scout, WARP Rescue, «револьвер» и Bearhole

Раздел WARP Scout в **Podkop BearGuard** построен вокруг отдельного проекта [**vernette/warpscout**](https://github.com/vernette/warpscout). Это не наш сканер и не переименованная копия: поиск доступных конечных точек Cloudflare WARP, измерение их качества, определение узла Cloudflare и региона выхода выполняет именно **WARPSCOUT**, созданный и развиваемый **vernette**.

Автору WARPSCOUT — отдельная и совершенно заслуженная благодарность. Проект решает практическую задачу, которую обычный клиент WARP почти не показывает пользователю: позволяет увидеть, через какой узел Cloudflare фактически строится путь, сравнить конечные точки, отбросить неудачные и выбрать рабочий вариант. Поддержка OpenWrt предусмотрена самим WARPSCOUT, поэтому здесь сознательно используется готовый специализированный инструмент вместо ещё одного собственного сканера.

Наша часть начинается там, где результат разведки нужно превратить в устойчивую работу роутера: установка и обновление WARPSCOUT, запуск из LuCI, разбор результатов, проверка пригодности маршрута для Telegram, хранение лучших кандидатов и аварийное переключение между ними.

#### WARP Revolver — страховка из нескольких проверенных WARP-маршрутов

WARP Rescue работает как «револьвер». После сканирования берутся не все найденные адреса, а только те WARP-конечные точки, которые прошли отдельную проверку доступа к Telegram. Из них собирается **магазин** кандидатов; он сортируется по качеству, сохраняется между запусками и используется как резервный набор.

Когда требуется аварийный маршрут, контроллер последовательно пробует кандидатов из магазина. Для каждого адреса он поднимает локальный SOCKS через WARPSCOUT и делает реальный запрос `getMe` к Telegram Bot API через этот SOCKS. Кандидат считается рабочим только после такой прикладной проверки, а не потому, что WireGuard/WARP формально поднялся. Удачный адрес остаётся активным и запоминается.

Если текущий WARP перестал работать, «револьвер» переходит к следующему кандидату. Если магазин исчерпан, выполняется **перезарядка**: новый Discovery в WARPSCOUT → повторная квалификация через Telegram → сбор нового магазина → запуск лучшего из прошедших кандидатов. Поэтому WARP Rescue страхует не один статический адрес, а целый заранее проверенный набор, способный обновиться самостоятельно.

#### Bearhole — аварийный bootstrap OpenWrt при блокировках

**Bearhole** предназначен прежде всего не для постоянного проксирования пользовательского трафика, а для ситуации, когда роутер нужно **починить или доустановить прямо в условиях блокировок**, а прямой доступ к GitHub, raw.githubusercontent.com, GitHub API, codeload или пакетным репозиториям OpenWrt уже не работает.

Bearhole не ведёт отдельный список прокси. Он собирает **тот же фактический пул маршрутов**, который уже известен `podkop_bot` и LuCI:

- основной Mixed Proxy Podkop/Forkop;
- дополнительные рабочие секции Podkop/Forkop;
- резервные SOCKS из транспортной цепочки бота;
- пользовательский прокси;
- активный WARP Rescue;
- прямой выход, когда политика его допускает.

Затем каждый маршрут проходит специальную системную квалификацию. Проверяется не абстрактный «Интернет есть», а именно то, что нужно для восстановления OpenWrt: главная GitHub, `raw.githubusercontent.com`, GitHub API, `codeload.github.com`, загрузка release-assets и настроенные репозитории `opkg`/`apk`. Маршруты получают состояние `VALID`, `DEGRADED` или `FAIL`; в рабочий набор Bearhole попадают только пригодные.

За счёт этого Bearhole можно использовать как **bootstrap-канал**: дать `opkg`, `apk`, `wget`, `curl` или установщику временный HTTP-прокси и через уже живой туннель скачать недостающий пакет, восстановить LuCI, обновить бот или снова подключить пакетный репозиторий. Если основной маршрут исчез, шлюз может перейти к следующему проверенному маршруту из того же общего пула.

#### `hwelp-proxy` — маленький нативный помощник Bearhole

Для Bearhole написан отдельный компактный прокси **`hwelp-proxy` на C**. Название — игра слов: английское *help* и староанглийское **hwelp**, «детёныш, медвежонок»; то есть буквально маленький помощник рядом с Bearhole.

`hwelp-proxy` слушает только loopback (`127.0.0.1`), принимает обычный HTTP-прокси и HTTPS `CONNECT` и умеет последовательно использовать несколько верхних маршрутов: прямой выход, SOCKS5/SOCKS5h или HTTP-прокси. Поддерживается авторизация SOCKS5 и HTTP, но учётные данные не пишутся в журнал. Перехвата TLS, TUN/TAP, `nftables`, sing-box или ucode внутри него нет — во время работы ему нужна только libc.

Ключевая особенность: список маршрутов хранится отдельно в `routes.conf`, и `hwelp-proxy` перечитывает его **на каждом новом клиентском соединении**. Поэтому Bearhole может переквалифицировать или переставить маршруты без перезапуска самого прокси. Получается маленький устойчивый шлюз для пакетного менеджера и аварийных загрузок, который не зависит от тяжёлого сетевого стека в момент, когда этот стек как раз и приходится чинить.

`hwelp-proxy` остаётся необязательным архитектурным пакетом и устанавливается по требованию. Его отсутствие не должно мешать установке или ремонту основного пакета BearGuard (`luci-app-podkop-bot`).

### Обновление

В одном месте собраны обновления трёх независимых частей:

- **веб-интерфейс LuCI** — проверка и установка новой версии IPK/APK;
- **Telegram-бот** — обновление с GitHub или установка локального файла `podkop_bot.sh`;
- **Podkop/Forkop** — проверка версии и запуск штатного установщика выбранного варианта.

Если GitHub недоступен напрямую, приложение может использовать уже работающий прокси-маршрут. Установка выполняется так, чтобы перезапуск `rpcd` не обрывал сам процесс обновления.

### Журнал

Просмотр последних сообщений бота, обновление списка и сохранение журнала. Диагностический архив скрывает известные чувствительные значения перед выдачей пользователю.

### Справка

Краткое описание назначения BearGuard, его разделов и границ ответственности между самим приложением, `podkop_bot` и Podkop/Forkop.

## Установка

Готовые пакеты публикуются в [GitHub Releases](../../releases). Команды ниже автоматически находят последнюю опубликованную версию, скачивают подходящий пакет во `/tmp` и устанавливают его.

Используется штатная утилита `jsonfilter`, входящая в OpenWrt.

### OpenWrt 24.10 и старее — opkg

```sh
U="$(wget -qO- https://api.github.com/repos/Medvedolog/luci-app-podkop-bot/releases/latest | jsonfilter -e '@.assets[*].browser_download_url' | grep '_all\.ipk$' | head -n1)"; [ -n "$U" ] && wget -O /tmp/luci-app-podkop-bot.ipk "$U" && opkg install /tmp/luci-app-podkop-bot.ipk
```

### OpenWrt 25.12 и новее — apk

```sh
U="$(wget -qO- https://api.github.com/repos/Medvedolog/luci-app-podkop-bot/releases/latest | jsonfilter -e '@.assets[*].browser_download_url' | grep '\.apk$' | head -n1)"; [ -n "$U" ] && wget -O /tmp/luci-app-podkop-bot.apk "$U" && apk add --allow-untrusted /tmp/luci-app-podkop-bot.apk
```

Для отдельного APK из GitHub Releases используется `--allow-untrusted`, пока пакет не устанавливается из настроенного доверенного репозитория.

### Зависимости

Обязательные зависимости основного пакета:

`libc`, `luci-base`, `jq`, `curl`.

`hwelp-proxy` не является обязательной зависимостью основного пакета и не должен блокировать его установку или восстановление.

## Совместимость

Поддерживаются OpenWrt 24.10 и 25.12+ с соответствующими пакетными форматами IPK и APK.

Приложение распознаёт несколько вариантов семейства Podkop и учитывает различия между их конфигурациями. Часть возможностей зависит от конкретного форка и версии sing-box. Для встроенного Tailscale/tsnet требуется сборка sing-box с соответствующей поддержкой.

Функции, которых нет в установленной версии Podkop/Forkop или sing-box, должны отображаться как недоступные, а не включаться принудительно.

## Сборка

Основной пакет состоит из JavaScript, shell-скриптов и файлов конфигурации и поэтому имеет архитектуру `all`/`noarch`.

Сборка выполняется через [owfeed](https://github.com/owfeed/owfeed): для OpenWrt 25.12+ создаётся APKv3, для OpenWrt 24.10 — IPK. Оба варианта собираются из одного подготовленного дерева файлов и затем проходят установочную проверку в OpenWrt через `owlab`.

Описание пакета находится в `owfeed.yml`, устанавливаемые файлы — в `root/`, сценарии пакетного менеджера — в `scripts/`. Процедура подписания и публикации описана в [RELEASING.md](RELEASING.md).

Импорт рабочей выгрузки в дерево репозитория выполняется через процесс `import-from-zip`, который принимает архив в `_incoming/` и раскладывает его по структуре проекта.

## Благодарности и использованные идеи

Проект вырос не в вакууме. Часть решений появилась благодаря существующим открытым проектам, их исходному коду и удачным практическим приёмам. Где использовалась идея, способ проверки или структура решения, а не буквальная копия кода, это именно техническое влияние; мы стараемся не приписывать себе чужую работу и не приписывать конкретному автору то, чего не можем подтвердить.

- [**vernette/warpscout**](https://github.com/vernette/warpscout) — автору **vernette** за WARPSCOUT: сам движок поиска и проверки конечных точек Cloudflare WARP, определение узлов и регионов выхода, поддержку OpenWrt, а также за практические идеи проверки пригодности сетевого маршрута. Часть подходов к прикладной проверке внешних сервисов в `podkop_bot` и LuCI развивалась с оглядкой на WARPSCOUT и была затем адаптирована под наши задачи.
- [**Medvedolog/podkop_bot**](https://github.com/Medvedolog/podkop_bot) — непосредственный источник транспортной логики, диагностики, значительной части проверок доступности Telegram/GitHub и внешних сервисов, а также установщика, встроенная копия которого поставляется с LuCI-пакетом. LuCI не скрывает это происхождение: веб-интерфейс во многих местах является визуальной и RPC-обвязкой уже проверенной логики бота.
- [**itdoginfo/podkop**](https://github.com/itdoginfo/podkop) — основной проект Podkop, его модель маршрутизации, UCI-конфигурация и сама экосистема, ради которой создавались бот и веб-интерфейс.
- [**yandexru45/podkop-evolution**](https://github.com/yandexru45/podkop-evolution) и [**yandexru45/netshift**](https://github.com/yandexru45/netshift) — за альтернативную ветвь развития Podkop, особенности конфигурации и совместимости, которые учтены в автоматическом определении вариантов и диагностике.
- [**ushan0v/podkop-plus**](https://github.com/ushan0v/podkop-plus) и [**ushan0v/forkop**](https://github.com/ushan0v/forkop) — за расширенную модель секций, URLTest, подписки, серверные службы и другие возможности, поддержку которых пришлось учитывать в боте и LuCI.
- [**slayer326/forkop**](https://github.com/slayer326/forkop) — Forkop X, чьи изменения в структуре и интерфейсе потребовали отдельной совместимости Tailscale/tsnet без вмешательства в исходный код самого форка.
- [**VizzleTF/podkop_autoupdater**](https://github.com/VizzleTF/podkop_autoupdater) — за шаблон установщика и идеи обнаружения рабочего транспорта через DoH. Эта атрибуция уже присутствует в README `podkop_bot` и сохраняется здесь.
- [**OpenWrt/LuCI**](https://github.com/openwrt/luci) — за платформу LuCI, RPC/UCI-модель и типовые приёмы построения приложений для OpenWrt.

Отдельно благодарим авторов проектов и скриптов, из которых в ходе разработки `podkop_bot` и LuCI заимствовались **идеи прикладных проверок сервисов, выбор контрольных URL, способы отличить формально поднятый туннель от реально пригодного маршрута и приёмы аварийного восстановления связи**. Там, где такая логика была перенесена в LuCI, она обычно была переписана под параллельный запуск, общий предел времени, работу через произвольный прокси-маршрут и единый формат результата, но происхождение идей от этого не исчезает.

Если в истории проекта обнаружится ещё один конкретный upstream, чей код или заметная идея были использованы и не перечислены здесь, его следует добавить в этот раздел, а не оставлять атрибуцию только в истории коммитов.
